# Skill: Learning Capture

How to extract structured, reusable insights from raw project notes, experiments, and conversations.

---

## Core Principle

**A learning isn't what you did — it's what you now know that you didn't before.**

Activities ("we built X") aren't learnings. Observations ("X worked because Y") are. The test: could someone apply this insight without doing your exact project?

---

## When to Use

Use this skill when:
- Debriefing after a project or experiment
- Converting meeting notes into insights
- Preparing content for newsletters or videos
- Building organizational knowledge from individual experience

Do NOT use when:
- Documenting procedures (that's process documentation)
- Recording decisions (that's decision logging)
- The insight is too context-specific to transfer

---

## Framework: The LEARN Structure

### L — Locate the Surprise
What was unexpected? What challenged assumptions?
- "We thought X, but actually Y"
- "Everyone assumes X, but we found Y"
- If nothing surprised you, dig deeper — or there's no learning

### E — Extract the Insight
State the learning in one sentence.
- Start with "We learned that..." or "It turns out that..."
- Make it specific enough to be actionable
- Make it general enough to apply elsewhere

### A — Anchor in Evidence
What proves this learning is real?
- Specific result or metric
- Observable behavior change
- Stakeholder feedback
- Comparison (before/after, with/without)

### R — Reason Why
Why did this happen? What's the underlying cause?
- "This works because..."
- "This failed because..."
- Understanding causation makes the learning transferable

### N — Next Application
Where else could this apply?
- Other projects
- Other teams
- Other contexts
- What would you do differently next time?

## Techniques

### The "We Thought / We Found" Frame
Forces you to articulate the delta between expectation and reality.

"We thought [assumption]. We found [reality]."

### The Five Whys (Lite)
Ask "why?" at least twice to get past surface observations.
- Observation: "The tool wasn't adopted."
- Why? "People didn't trust the outputs."
- Why? "The first version had visible errors."
- Learning: Early accuracy problems create lasting credibility debt.

### The Transferability Test
Ask: "Could someone in a different project use this insight?"
- If no → it's a project note, not a learning
- If yes → you've extracted something valuable

### The Counter-Factual
"If we had known this earlier, we would have..."
This surfaces the practical value of the insight.

### Quantify When Possible
- Weak: "It was faster"
- Better: "It was noticeably faster"
- Best: "It reduced time from 2 hours to 15 minutes"

---

## Anti-Patterns

### The Activity Log
Listing what happened without extracting what was learned.

**Fix:** Ask "So what?" until you hit an insight.

### The Obvious Insight
Stating something everyone already knows.

**Fix:** Apply the surprise test. If no one would say "huh, interesting," dig deeper.

### The Unanchored Claim
Asserting a learning without evidence to support it.

**Fix:** Add the "we know this because..." clause.

### The Island Learning
Insight that only applies to this exact situation.

**Fix:** Abstract one level. "This specific vendor was slow" → "Vendor responsiveness predicts project timeline more than stated capacity."

### The Missing "Why"
Knowing something works without understanding why.

**Fix:** Push for causation. Pattern without explanation doesn't transfer well.

## Example

### Raw Input (from project debrief)

> "We spent three weeks building a custom GPT for the audit team. They used it for about a week and then stopped. Feedback was that it was 'too slow' and 'didn't understand their terminology.' We tried to fix it but couldn't get adoption back."

### Structured Learning

**Learning: Early adoption failures create lasting credibility debt**

**What we did:**
Built a custom GPT for the audit team to assist with workpaper review. Initial version had latency issues and struggled with domain-specific terminology.

**What we learned:**
First impressions in tool adoption are disproportionately sticky. Users who had a poor initial experience didn't return even after improvements were made. The "too slow" perception persisted even when latency was fixed.

**So what?**
For AI tools, a mediocre launch is worse than a delayed launch. Users form judgments quickly and update them slowly. This suggests:
- Beta test with friendly users before broad rollout
- Launch with a narrow, polished use case rather than broad, rough capability
- Have a re-launch strategy if initial adoption stalls

**Evidence:**
- Usage dropped from 47 sessions (week 1) to 8 sessions (week 3)
- Post-fix survey: 6/8 respondents still cited "speed" as concern despite measured 3x improvement
- Similar pattern seen in two other tool rollouts

**Try this:**
Before your next tool launch, identify 3-5 champion users for soft launch. Only go broad when champions report consistent value.

## Quick Reference

### LEARN Structure
- **L**ocate the surprise (what was unexpected?)
- **E**xtract the insight (one sentence)
- **A**nchor in evidence (what proves it?)
- **R**eason why (what caused this?)
- **N**ext application (where else does this apply?)

### Key Questions
- "We thought... we found..."
- "If we had known this earlier, we would have..."
- "Could someone in a different project use this?"
- "Why?" (ask twice)

### Tests
- Surprise test: Would someone say "huh, interesting"?
- Transferability test: Useful outside this exact context?
- Evidence test: Can you prove this isn't just opinion?
